# Contributing to 5120 Team 18

Thanks for contributing. This repository uses a lightweight pull-request workflow so the team can review work and keep main stable.

## Before starting

1. Check the Issues page and confirm the task owner.
2. Create or update an issue with clear acceptance criteria.
3. Branch from the latest main branch.

## Branch names

Use a short, descriptive name with one of these prefixes:

- feature/ — new functionality
- fix/ — bug fixes
- docs/ — documentation only
- test/ — test changes
- chore/ — maintenance and configuration

Example: feature/user-interview-dashboard

## Commits

- Keep each commit focused on one logical change.
- Use an imperative summary, for example: feat: add interview filter.
- Never commit secrets, credentials, private research data, or generated dependency folders.

## Pull requests

Every pull request should:

- Link the relevant issue.
- Explain what changed and why.
- Include testing or verification evidence.
- Include screenshots for visible interface changes.
- Be small enough to review comfortably.
- Receive at least one teammate review before merging.

Prefer squash merging unless preserving individual commits is useful.

## Definition of done

A task is complete when:

- Acceptance criteria are met.
- Relevant tests and checks pass.
- Documentation is updated.
- No secrets or private participant data are included.
- A teammate has reviewed the pull request.
- The pull request is merged and the issue is closed.

## Communication

Use issue comments and pull-request discussions for decisions that affect implementation. Summarise important meeting decisions under docs/ so they are easy to find later.
